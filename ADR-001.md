# ADR-001 — Sincronização de estado do kanban: Yjs (CRDT) + LWW no servidor

**Status:** Aceito (M2) | **Data:** 2026-09-26 | **Decidido por:** juízes NVIDIA (rodada 2 do plano: "LWW para colaboração real é UX quebrada — perda de edição silenciosa")

## Contexto

O M1 usava last-writer-wins (LWW) nos movimentos de cards: dois clientes movendo o mesmo
card simultaneamente resolviam pelo último evento — **perda silenciosa de edição** (a
posição de um usuário era sobrescrita sem aviso).

## Decisão

1. **Estado do CARD (posição/texto): Yjs CRDT** — convergência garantida: updates aplicados
   em ORDEM DIFERENTE nos clientes produzem o MESMO estado final, sem perda nem duplicação.
   Teste provando: `test/sync-yjs-test.mjs` (convergência + movimento via delete/insert).
2. **Membership do board (quem é dono, convites): LWW no servidor** — simples e suficiente:
   não é editável concorrentemente pelos clientes.

## Consequências

- (+) Sem perda silenciosa: renomeação concorrente + movimento simultâneo convergem
  (testado: 'a-renomeado' + 'b' em ambos os docs)
- (+) Zero servidor de sinalização externo: updates binários trafegam pelo MESMO relay ws
- (+) Offline-friendly: cada cliente tem o Y.Doc local, sincroniza ao reconectar
- (−) Dependência `yjs` (~300KB no servidor, ~90KB gzip no cliente) — aceitável
- (−) O servidor mantém um Y.Doc por quadro (memória: ~1KB/quadro ativo)

## Alternativas descartadas

- **LWW puro** — perda silenciosa (o problema)
- **Operational Transform (OT)** — complexidade de servidor central alto
- **Automerge** — CRDT equivalente, bundle maior no cliente (2020, trellis)
